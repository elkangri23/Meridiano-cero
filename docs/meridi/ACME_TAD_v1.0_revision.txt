A.C.M.E.

Documento de Arquitectura Técnica (TAD) · Versión 1.0 — propuesta para aprobación

27 de octubre de 2026  |  Estado: diseño técnico; no constituye implementación

Documento complementario al GDD v0.1 aprobado. El GDD gobierna las mecánicas; este TAD define cómo construirlas y operarlas.

1. Resumen ejecutivo

A.C.M.E. será un videojuego detectivesco internacional, web y de código abierto (AGPL-3.0-only), instalable por terceros y con una instancia pública gratuita. La lógica de investigación será autoritativa y determinista en el backend; los modelos de IA generarán expedientes validados e interpretarán/narrarán acciones sin poder alterar la verdad del caso.

Desarrollo inicial en ordenador personal con modelos locales mediante Ollama o LM Studio; uso de pnpm para desarrollo y Docker Compose para servicios y distribución.

Producción futura en VPS: registro obligatorio, partidas persistentes y FreeLLMAPI como IA proporcionada por el administrador, sin configuración para el jugador.

Instalaciones independientes: cualquier persona podrá desplegar A.C.M.E. y configurar su propio proveedor o endpoint compatible; no dependerán de la instancia pública.

Diseño modular, una sola base de código, despliegues configurables y seguridad por defecto.

3. Vista lógica y límites de confianza

Navegador React → API HTTPS Fastify → servicios de dominio (motor, expedientes, usuarios, límites) → PostgreSQL. El servicio de IA invoca adaptadores hacia APIs externas o endpoints locales. Trabajos largos de generación/validación se ejecutan en un worker separado con cola persistente.

El navegador es no confiable: solo recibe datos revelados al detective. El backend valida autenticación, permisos, acciones, tiempos, estado y cuotas. Las respuestas de la IA son también no confiables: se validan por esquema, contra el expediente y por reglas del motor.

5. Modelo de dominio

User, Credential/Session, DetectiveProfile, CareerRecord, Settings y AIConfiguration (ámbito usuario o instalación).

CaseDefinition: identificador, versión, semilla, hechos inmutables, culpable(s), NPCs, ciudades, lugares, pistas, pruebas, reglas de resolución, duración, modo y dificultad.

CaseRun: instancia jugable, usuario, reloj, acciones, inventario, pruebas reveladas, estados de NPC, solicitudes, órdenes, detenciones y resultado.

ActionLog: evento secuencial, entrada normalizada, coste temporal, cambios de estado, versión del motor y resultado; permite auditoría y depuración.

ProviderUsage: proveedor, función, modelo, tokens/estimación, latencia, coste estimado, errores y usuario, minimizando contenido personal.

La definición completa del caso se conserva en el servidor. El cliente recibe proyecciones filtradas según lo descubierto. La integridad del caso se protege con versión de esquema y hash; una partida queda asociada a una versión inmutable.

6. Contrato de acciones y motor

Flujo: texto libre → intérprete IA produce intención estructurada → validador de esquema → resolución determinista del motor → persistencia transaccional → narrador IA limitado a hechos autorizados → respuesta visual. Si el intérprete falla, se solicita aclaración sin alterar el estado.

Entrada normalizada

Ejemplo

type

inspect | collect | talk | travel | analyze | communicate | request_warrant | detain | finish

targetId

ID existente y visible/accesible, cuando proceda

parameters

Criterios concretos de inspección, mensaje o destino

expectedVersion

Versión de CaseRun para control de concurrencia

idempotencyKey

Evita doble ejecución por reintentos

Reglas: solo el motor puede cambiar tiempo, inventario, hechos descubiertos, órdenes y desenlace. La IA no puede crear lugares investigables, evidencias, resultados de laboratorio ni información secreta. Las acciones por lotes se ejecutan secuencialmente; hallazgos no interrumpen el lote, pero imposibilidad sí exige confirmación para continuar.

7. Reloj y tareas asíncronas

El tiempo del juego avanza únicamente por acciones con coste; lectura, escritura, conversaciones y espera fuera del juego no lo hacen. Antes de ejecutar, la API ofrece estimación de duración y tiempo restante. Si una acción supera el plazo, se trunca al instante exacto del vencimiento y se cierra el caso automáticamente.

Análisis, mensajes pendientes y otros jobs internos se programan con timestamps del reloj del caso, no con el reloj real. Al avanzar el tiempo se procesan eventos vencidos en orden estable. Retrasos raros de viaje se calculan desde una semilla persistida y se consideran durante la validación de solvencia.

8. Generación, validación y simulación

Pipeline: plan del delito → geografía real verificable → personajes y conocimientos → red de pistas/rutas → normalización JSON → validación determinista → revisión semántica IA → simulación de rutas y límites temporales → persistencia inmutable. No se habilita jugar hasta superar todas las puertas de calidad.

Validaciones duras: referencias válidas, coherencia temporal, culpable y objetivos fijados, pistas accesibles, múltiples rutas, límites de tiempo, órdenes y detenciones alcanzables, ausencia de softlocks.

Validación semántica: plausibilidad, tono Familiar/General, geografía, diálogos y consistencia de motivaciones. La IA revisora no sustituye las pruebas deterministas.

Simulaciones: al menos rutas de éxito alternativas y rutas de error; se incluyen retrasos y acciones no productivas dentro de márgenes definidos.

Casos rechazados se regeneran con presupuesto máximo de intentos y error claro si no se obtiene uno válido; nunca se sirve un expediente incompleto.

9. Adaptadores y configuración de IA

Interfaz común por función: generateCase, validateCase, interpretAction, narrateResult y converse; cada una recibe esquemas y límites específicos. Configuración independiente para generador, validador y director de partida. Proveedores iniciales: Ollama, LM Studio, OpenAI-compatible, OpenAI, Anthropic, Gemini; FreeLLMAPI según protocolo verificado.

Cada adaptador declara capacidades (JSON estructurado, contexto, herramientas, streaming), timeout, reintentos acotados y estimación de coste. Un test de conexión no garantiza calidad de generación: se ofrecen pruebas funcionales y avisos para modelos insuficientes. El cambio de modelo no altera casos ya fijados.

En desarrollo local, Ollama corre preferentemente fuera de Docker; la API usa una URL configurada (host.docker.internal en Docker Desktop, sujeto a plataforma). En la instancia pública, las conexiones hacia endpoints de usuarios estarán deshabilitadas por defecto; el administrador podrá habilitarlas solo con controles reforzados.

10. Seguridad de IA y endpoints

Nunca publicar claves de FreeLLMAPI ni otros proveedores en frontend, repositorio o logs; secretos mediante variables de entorno/gestor de secretos.

Cifrado de credenciales de usuarios en reposo con clave de cifrado separada; no prometer cifrado extremo a extremo si el servidor debe usarlas.

SSRF: bloquear rangos internos, loopback, metadatos cloud, redirecciones no verificadas, esquemas no HTTPS en público; validar DNS y destino efectivo en conexión.

En instalaciones privadas permitir acceso a Ollama local mediante política explícita del administrador; no reutilizar las restricciones de la instancia pública sin considerar su entorno.

Prompt injection: documentos y mensajes NPC tratados como datos; salida IA validada por esquema y lista de hechos permitidos.

Límites por usuario, IP, modelo, función y gasto global; cola con concurrencia máxima, cancelación, backoff y corte de emergencia.

Sesiones con cookies HttpOnly, Secure y SameSite; CSRF según diseño, protección de login, recuperación de contraseña y políticas de retención de datos.

Para eventos de generación y mensajes se puede comenzar con polling y evolucionar a SSE; no se requieren WebSockets desde el primer prototipo. Todas las rutas se versionarán (/api/v1).

12. Experiencia visual y accesibilidad

Interfaz de una pantalla con ventanas retro móviles, minimizables y comparables; reloj y plazo siempre visibles. Texto libre para acciones, mapa interactivo, expediente, comunicaciones, laboratorio y terminal de inteligencia. El servidor solo entrega escenas y objetos autorizados; no se ocultan secretos únicamente con CSS.

Objetivo WCAG 2.2 AA: navegación por teclado, foco visible, lectores de pantalla, tamaño de fuente y escala, alto contraste, modos de daltonismo, reducción de movimiento, etiquetas descriptivas sin revelar pruebas ocultas. TTS con Web Speech API como primera opción y subtítulos/texto siempre disponibles. Audio y música nunca son fuente exclusiva de pistas.

16. Trabajo con agentes de programación

Un arquitecto conversacional inspecciona el repositorio, propone alcance y plan y solicita aprobación antes de tareas grandes. Agentes especializados pueden trabajar en ramas/worktrees separados para motor, IA, frontend, persistencia y QA. Integración mediante contratos, revisión de código y CI; ningún agente debe modificar silenciosamente el GDD o las reglas cerradas.

Cada tarea debe indicar: objetivo, archivos afectados, criterios de aceptación, pruebas, riesgos, dependencias y entregables. Las decisiones de arquitectura se registran como ADR en docs/adr/.
